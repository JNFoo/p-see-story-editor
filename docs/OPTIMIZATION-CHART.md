# Chart of Optimization Impacts: Story Editor

**Project:** Story Editor, a single-file, offline editor for choose-your-own-adventure stories (536,247 bytes plain and 249,194 bytes as delivered, zipped, after the October 12 bug-fix round; it was 530,633 and 246,577 after the October 8 night round and 462,439 and 219,404 after the earlier October 8 rounds; before them 456,777 bytes, gzip 165,467, after the night round (programming lessons 1 to 7 and 10, which added about 4.2 KB for spare-copy saves, the error log, size budgets and the options table); it was 452,560 bytes (gzip 165,182) after the evening round and 434,354 bytes (gzip 158,329) after the lite export. That round cost +18,206 bytes for the speed report, the place-code module and styles (carried by the editor because the Play tab carries every module; 3.2 KB of that), the short-id and grouping code, and the new tests' hooks; 484,759 bytes before the features and 597,076 right after them). Authors write pages and choices, check every path, and export each story as one small HTML game. Parts: a story model and checker (`core.js`), the Map (`maplayout.js`, `ui4-map.js`: SVG drawings with eight views, including the River and the Story shape), the player used by the Play tab and by every exported game (`player.js`, `game.css`), and the editor screens (`ui1` to `ui5`, `ui.css`).

**Main test devices:** the owner's Firefox on Windows, an Android phone in Chrome, and iPhone or iPad (Safari engine). In the cloud container (Linux, 2 cores, 8 GB): stock Firefox 158 (the owner's version) is the main test browser, driven through Puppeteer; Playwright Chromium 141 runs only in the full check before a file is delivered. Firefox 142 was dropped on October 8 at the owner's request; mentions of it below are history.

Build 536,247 bytes plain, 249,194 zipped. Limitation: still nothing has run on a real Android phone or iPhone; touch was tested with Chromium's phone emulation only. How each impact was measured:

- **Measured today:** on October 7, the old and new code were run on the same stories on the same machine (scripts in the scratch folder `dr/`). Timings vary about 30% from run to run, so only bigger differences count.
- **Measured in the round:** numbers recorded on October 4 in the audit and review reports and in saved scratch files.
- **Test only:** shown by a check passing, with no number.
- **Not measured / not isolated:** it helped or was needed, but no before and after exists.
- **Container:** a cloud machine without a graphics chip; direction only.

### Measuring what actually works

**The editor**

1. **Size:** measure the built file and each part, raw and gzipped, from the file itself (`dr/measure.py`). The font is base64, so it counts as 4/3 of its file size and barely compresses (76%).
2. **Exported game size:** run the real `buildGameHtml` in Node with `vm`, using the assets read from the built file (`dr/expo.js`). For "before" numbers, run the old code the same way from the October 4 backup `scratchpad/editor-backup-2146/` (`dr/oldnew.js`, which reproduced the earlier 66,630 and 60,402 byte files exactly). Always use the same story file for both.
3. **Checker:** load only `core.js` in Node with `vm`. Warm up once, average several runs, and always print how many situations were reached and whether the check stopped. Use synthetic stress stories (`audit/perf2.js`, `dr/bench.js`) and put old and new in the same run. Run each comparison twice; the same case came out at 124 and 180 ms in two runs, so only trust differences above about 30%.
4. **Map layout:** load `core.js` and `maplayout.js` in Node (`ml.js`) for layout milliseconds. In the browser (`dr/mapviews.js`) the view switch includes two animation frames (about 33 ms), so anything near that is "no cost". Count SVG elements as the cost that grows with story size.
5. **Start-up:** Playwright navigation timing, a fresh context each time, median of 7 (`dr/startup.js`), in both Chromium and Firefox. The splash lasts about 2.5 s and tests wait 4.2 to 4.3 s before touching the page.
6. **Memory:** Chromium's `JSHeapUsedSize` through the debugger connection for the editor; Node's `process.memoryUsage()` with `--expose-gc` for the checker. Firefox has no equivalent here, so Firefox memory is not measured.
7. **Drawing smoothness is not measurable in the container.** The Apple Press project learned that frame-rate labs report about 60 fps while the owner sees stutter, because painting and compositing fall behind while script still runs on time. Use the container for correctness, layout and sizes. For smoothness (map pan and zoom, the splash, any new animation) ask the owner to look in Firefox on Windows and on the Android phone, or use the speed report (#48; Options → Speed report…).
8. **The Firefox lesson:** Chrome-only results do not carry over. Firefox 142 in the container started the exported game in 104 ms against 13 ms in Chromium, and the editor in 347 against 250 ms (DOMContentLoaded, median of 7). Both are small, but they are different engines with different bottlenecks. Firefox also lacks the file-save window (it downloads a copy), the themed drop-downs and the debugger connection, so some tests are Chromium-only on purpose. Run correctness suites in both engines. One caution to test with the owner: Firefox's "resist fingerprinting" privacy setting is known to scramble canvas read-back (Apple Press lost its retro pictures to it) and to coarsen timers; this project reads no canvas, but `performance.now()` feeds the "speed" score in Compare views, so test that dialog with the setting on.

**The game**

- It is a static page. Measure bytes (raw and gzipped), time to the first page, and correctness in Chromium, Firefox and phone emulation. Check that it has no `http` text outside the story data, carries the CSP, plays through, resumes after reload, and shows no console errors (all in `real.js`).
- The page change animation is a 0.28 s fade with a 4 px move (opacity and transform only), switched off by `prefers-reduced-motion`. Keep any new animation in that class.

### Rules learned for this project

- **Edit the parts, build, then test the built file.** Tests open `/home/claude/twine/editor/story-editor.html` directly. Run tests from the scratchpad folder, not from the editor folder (a stray `shots/` folder once landed in the project).
- **The rules functions are copied as text into every game.** They are listed in `KL_RULES` in `core.js` (`klHas`, `klCondOk`, `klVisibleBlocks`, `klStatMap`, `klInit`, `klAdd`, `klChoose`, `klVisibleChoices`, `klShown`, `klArrive`, `klTarget`, `klOdds`), plus `klPlayer`. `build-game.mjs` copies exactly that list, and the contract test fails if a `kl…` function exists that is not on it. They may call only each other and the browser's own functions, never other helpers from `core.js`. Rename or add one in `KL_RULES` in the same change.
- **A new optional game feature is a module.** Write `klFeat<Name>(P)` in `player.js` (it adds itself to the core through hooks and registers in `KL_FEATS` at the bottom), list the name in `KL_FEATURE_ORDER` and teach `klFeatures()` in `core.js` when a story needs it, and put its styles in a section of `game.css` that starts with `/*@part name*/`. `contract.mjs` fails the build if the function, the registration, the styles or the picking rule is missing or inconsistent, or if a story that needs the feature would be exported without it. Never let the core call a module directly; use a hook, so a game without the module still runs. Run `top10-lite.js` in both browsers before shipping a new module: it plays lite and full games side by side.
- **The small typeface is checked at build time.** `KL_LITE_FONT` in `core.js` lists the characters it may be used for; `build.py` stops if the small font lacks one of them. Changing either means changing both.
- **The shipped editor is shrunk; the sources are not.** Use `STORY_READABLE=1 python3 build.py` to get readable code with real line numbers when chasing an error in the browser, then rebuild normally before delivering.
- **The checker is part of every feature, and the build enforces it.** `FIELD_CONTRACT` in `core.js` lists every field of a project, passage, block, choice and item as `rules` (changes what a player can do or see) or `display`. A new field that is not listed fails the build. A `rules` field must also be read by `analyze()` (the test watches which fields the checker touches) and survive `exportStory`. Then extend the random story maker in `contract.mjs` so some random stories use the new thing; the test compares the checker with a brute-force play of the real game functions (pages reached, endings, stuck pages, usable choices, roll outcomes, exact situation counts). A feature is not done until `python3 build.py` prints "contract ok". `fuzz.js` remains as a second, independent check. Numbers and dice multiply situations (see #29), so keep the 200,000 limit and the "not checked" message honest.
- **The checker never calls something impossible when it merely stopped.** Keep that wording and the "stopped after 200,001 situations" note.
- **Hidden does not mean removed.** Features turned off under Options → Advanced still work in games. The Check tab says so under "Good to know" (`editorNotes`). A new Advanced switch (the owner chose a fourth, "Game") must do the same.
- **Exports are lean:** leave out any field equal to its default, and make sure the player treats a missing field as that default. Every new field needs one.
- **Story text is only ever inserted as text** (`textContent`), never HTML.
- **The font has a fixed character list** (ASCII, Latin-1, curly quotes, dashes, ellipsis, a few arrows). Characters outside it fall back to the device's font. The player itself uses "·", "…" and "→"; the arrow is not in the font.
- **Animations:** transform and opacity only; add every new one to the `prefers-reduced-motion` rules; never more than 3 flashes in a second over a large area, and no large saturated red flashes (WCAG 2.3.1). Avoid animating `filter`, `box-shadow` or `backdrop-filter`.
- **Do not use `:has()`, `inset` or other new CSS in `game.css`** (iOS 13.4 and Firefox 74 are the floor). `ui.css` currently has no `:has()` either; keep it that way.
- **Changing a menu label breaks tests.** It happened twice (the Options and File renames gave TimeoutError). Update the test strings in the same change. The same goes for class names: a new class that reuses an old name silently inherits its style (`.keys` from the shortcuts list squashed the new Key pages row, and `.swatch` from the map legend squashed the color buttons; they became `keypages` and `palbtn`). Before adding a class, search `ui.css` for it.
- **Tests need patience at start-up and a clean game state.** The splash lasts about 2.5 s, so wait 4.2 s after loading the editor. Exported games on `file://` share one storage area, and a game saves its place shortly after loading, so clearing storage once can be overwritten; clear, reload and check the first page, and retry (see `open()` in `top10-player.js`).
- **Run Prettier on changed parts before the final build** (`npx prettier --write` on the `.js` and `.mjs` files). It does not touch comments or behavior, but it grows the file a little (578 → 583 KB this round).
- **Menu text rule:** keep File and Options labels short; put the explanation in the tooltip. "Game options…" appears in Options only while the Game switch is on.
- **Screenshots can be stale.** The image viewer once showed a cached file; save new shots under new names.
- **Spelling:** American English everywhere. The check used on October 5 was a case-insensitive search for `colour|grey|centre|neighbour|behaviour|favour|organis|recognis|cancelled|labelled|tick(ed|s)`. `aria-labelledby` is the standard attribute and stays.
- **Save and Undo:** a remembered file belongs to an undo epoch, and opening or importing a story clears it, so Save never writes one story into another's file. Do not weaken this.
